# 整部经翻译（分块 + 滚动上下文）

一框 5000 字译不了一部经。逐段各译各的，同一个术语在前后段会被译成不同说法，
越往后漂得越远——这是长文机器翻译最主要的失败模式。

对策取自 Dharmamitra 官方 agent starterpack 的翻译流程：
**把已经译出来的上文回喂进下一块的 `context`**，让每一块都读得出前文是谁译的。

代码在 `src/document.js`（纯函数 + 驱动器，不碰 DOM），界面在 `src/ui.js` 的「整部经模式」一节。

## 切块规则

| 参数 | 值 | 理由 |
|---|---|---|
| 每块句数上限 | 5 | 官方建议 3–5 句 |
| 每块字数上限 | 260 | 汉文一句常 10–40 字，大致对应 3–5 句 |
| 单句硬上限 | 600 | 超过就只能退让切分 |

- **绝不切断一个句子。**
- **块不跨段落**：段落是天然单位（偈颂、品节），段末即使不满 3 句也断开，
  免得偈颂和长行散文粘在一块里。
- 断句认汉文句读（`。！？；`，连带 `」』` 收尾引号）、西文 `.!?`、藏文 shad `།`。
- 没有句读的偈颂会超过单句硬上限，此时按 `，、` 退让切分，并把该块标记 `forced: true`
  —— 这种块的译文质量本来就该被怀疑。
- 每块送上游时排成**一句一行**。官方文档说后端偏好这个排版，句对齐与译例检索都靠它。

## context 怎么装

按优先级排，装不下就**从底下丢**，而且是**从那一节往下全丢**——
一个便宜的低优先级小节挤掉一个贵的高优先级小节，就不是「drop from the bottom」了。
总量卡在 400 词（`countWords`：汉字按字算，其余按空白分词）。

1. **已译上文**（默认回喂最近 3 块）
2. 用户自带的旧译本片段
3. 本块命中的实证术语对照
4. 已定的专名
5. 一句话语体提醒

第 1 项有特权：连一块都装不下时**截断保留末尾**，而不是整节丢掉。
丢了它，这个功能就退化成逐段各译各的。理由也在官方文档里——
一份用了这些术语的上文，本身就隐含了术语表，所以它排在术语表前面。

## 缓存

缓存键刻意**不含** `context`。佛典里同一段程式化句子会反复出现，命中缓存意味着它们
前后被译成同一个说法——这正是整部经模式想要的一致性，也省掉重复请求。

## 反馈环

每 5 块暂停一次，显示已译块数并提示「看看术语对不对，要调就改译风设置再继续」。
官方文档把短反馈环列为对付漂移的主要手段：等整部译完再发现术语错了，代价太大。
随时可停止，已译部分保留并可导出。

## 测试

- `tests/document.test.mjs` —— 断句、切块、context 装配、驱动器（27 条）
- `scripts/smoke-static-site.mjs` —— 真浏览器跑一遍三块的文档，**在拦截器里查请求体**，
  断言第 N 块的 `context` 里含有第 N-1 块的译文

这两处的关键断言都做过变异测试：把回喂去掉、把「从底下丢」改成「跳过继续装」、
让出错后继续往下译、取消段落断块，四种改法都能让对应测试变红。

## 限流

⚠️ 实测 2026-08-15：上游约 **10 次请求/分钟**后开始回 429，**不带 `Retry-After`**，约 80 秒恢复。
一部经二三十块，不处理就跑到一半断掉。所以：

- 每块之间至少隔 `MIN_INTERVAL_MS`（6 秒），29 块的经约 3 分钟。
- 撞上 429 按 20 秒起步递增退避，最多 4 次，期间界面显示还要等多久。
- 只对限流与 5xx 重试；参数错、语种不支持这类立刻放弃。

## 效果实测

《佛遺教經》29 块，同条件跑两遍只改「回不回喂上文」，结论见 `eval/RESULTS.md`：
最高频术语「比丘」从 monks/bhikṣus 来回摇摆变成 21/22 一致，「世尊」从 4 种收敛到 2 种，
其余五条打平、零条变差；**总体覆盖率指标看不出差别**（0.965 vs 0.944，n=18 属噪声）。

**所以文案上只能说「把前文的译法带给后文」，不能说「消除术语漂移」。**

## 已知限制

- 只对**单一语种全文**生效。多本合参要的是同一段落的多语种写本，两者互斥。
- 术语一致性靠上下文**诱导，不是强制**。术语本身多义（如「功德」）或本来没在漂的地方，
  它什么也改变不了。真正能强制的是用户自己的术语表（对应 foguang.ai 的 "My glossary"）。
- 一部长经会发很多次请求。已做缓存、限速与失败即停，但仍应对上游用量心里有数。
